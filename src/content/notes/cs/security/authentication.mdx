Authentication is the process of establishing that a user or system is who it claims to be. Modern applications rarely accomplish this with a single password check: they combine evidence of identity, additional verification factors, and mechanisms for remembering authenticated users across requests. Understanding the distinction between authentication, authorization, sessions, tokens, and delegated identity explains how a login becomes a continuing, controlled relationship between a user and an application.

## Passwords: proving knowledge of a secret

A password is an example of a knowledge factor: something the user knows. The server compares the submitted credential against a stored password verifier to determine whether the user knows the correct secret.

A secure system should not store passwords as plaintext. Instead, it stores a salted, deliberately expensive password hash, typically produced using a function such as Argon2id. During login, the server applies the same password-hashing procedure to the submitted password and checks the result against the stored verifier. The salt prevents identical passwords from automatically producing identical stored values, while the computational cost makes large-scale guessing more expensive.

Passwords have a fundamental weakness: they can be guessed, reused across sites, phished, or stolen from compromised systems. Even a strong password provides limited protection if an attacker can obtain it and replay it elsewhere. Password managers help by generating unique credentials for each service, reducing the damage caused by reuse.

Password hashing also illustrates an important distinction: authentication does not require storing the secret itself. The system needs enough information to verify a claim, not necessarily to reconstruct the original credential.

```python
import hashlib
import hmac
import secrets
import time

salt = secrets.token_bytes(16)                                # unique per user: equal passwords store differently
verifier = hashlib.scrypt(b"correct horse battery staple", salt=salt, n=2**14, r=8, p=1, dklen=32)
t = time.perf_counter(); hashlib.scrypt(b"guess", salt=salt, n=2**14, r=8, p=1, dklen=32); ms = (time.perf_counter() - t) * 1000
print(f"one scrypt verification costs ~{ms:.0f} ms; plain SHA-256 costs microseconds")
def check(pw): return hmac.compare_digest(verifier, hashlib.scrypt(pw, salt=salt, n=2**14, r=8, p=1, dklen=32))
print("right password:", check(b"correct horse battery staple"), "| wrong password:", check(b"letmein"))
# one scrypt verification costs ~160 ms; plain SHA-256 costs microseconds
# right password: True | wrong password: False
```

That deliberate slowness costs a legitimate login a fraction of a second, but makes an attacker's billions of guesses unaffordable.

## Multi-factor authentication: combining independent evidence

Multi-factor authentication (MFA) strengthens authentication by requiring evidence from at least two different categories:

- Knowledge: something you know, such as a password or PIN.
- Possession: something you have, such as a hardware security key or authenticator device.
- Inherence: something you are, such as a fingerprint or face characteristic.

Two passwords are not two factors; they belong to the same category. A password plus a one-time code generated by an authenticator app combines different kinds of evidence.

MFA reduces the chance that stealing one credential is sufficient to impersonate the user. However, its effectiveness depends on the mechanism. SMS codes can be exposed through SIM-swapping or interception. Time-based one-time passwords can still be stolen through phishing. Phishing-resistant methods, such as properly implemented FIDO2/WebAuthn passkeys and security keys, bind authentication to the legitimate website or application, making it much harder to reuse captured credentials on a fake site.

MFA does not eliminate every attack. An attacker may steal an already authenticated session, manipulate a user into approving a fraudulent login, or compromise the endpoint itself. Authentication strength therefore depends not only on how many factors are required, but also on how they resist the attacks relevant to the system.

Authenticator apps use **TOTP**: both sides compute an HMAC of the current 30-second time window with a shared secret and keep six digits. This is the real algorithm, running live in your browser:

<TotpClock />

```python
import hmac
import hashlib
import struct

def totp(secret, t, digits=8, step=30):
    counter = struct.pack(">Q", t // step)
    h = hmac.new(secret, counter, hashlib.sha1).digest()
    o = h[-1] & 0x0F                                          # dynamic truncation
    return str((struct.unpack(">I", h[o:o + 4])[0] & 0x7FFFFFFF) % 10**digits).zfill(digits)
print("t=59 ->", totp(b"12345678901234567890", 59), "(RFC 6238 says 94287082)")
# t=59 -> 94287082 (RFC 6238 says 94287082)
```

## Sessions: remembering that authentication happened

HTTP is fundamentally stateless: each request is independent unless the application adds a mechanism to associate requests with a continuing user identity. A session provides that continuity.

After a successful login, the server creates a session record and gives the browser a session identifier, commonly stored in a cookie. On subsequent requests, the browser sends the cookie, and the server uses its identifier to retrieve the corresponding session state.

The identifier is not the password. It is a temporary credential that effectively says, “This request belongs to an already authenticated session.” If an attacker steals it, the attacker may be able to impersonate the user without knowing the password or repeating MFA. This is called session hijacking.

A secure session design uses unpredictable identifiers, HTTPS, appropriately configured cookies such as `Secure`, `HttpOnly`, and `SameSite`, session expiration, and rotation after important authentication events. Logout should invalidate the session on the server when server-managed sessions are used. Changing a browser cookie alone does not necessarily revoke a stolen credential.

Sessions are especially useful for traditional web applications because the server retains control over the session's state. It can invalidate a session immediately, track activity, and enforce policies centrally.

## Tokens: carrying authorization or identity information

A token is a piece of data that grants some defined capability or conveys some defined information. Unlike a traditional session identifier, a token may contain claims about a user, an application, or the permissions associated with a request.

A common format is the JSON Web Token (JWT). A signed JWT contains a header, a payload of claims, and a cryptographic signature. Claims might identify the subject, issuer, intended audience, and expiration time. A recipient verifies the signature and relevant claims before trusting it.

A crucial distinction is that a signed token is not necessarily encrypted. Its payload may be readable by anyone who obtains it. A signature helps establish that the token has not been altered and was issued by an entity holding the appropriate signing key; it does not automatically conceal the contents or guarantee that the token has not been revoked.

Tokens can be opaque too. An opaque token contains no directly interpretable claims for the recipient; the application or authorization server must look it up or otherwise validate it. Therefore, “session versus token” is not a strict choice between server-side and client-side state. A session identifier is itself a token in the broad sense, and a JWT can be used within a session-oriented architecture.

You can see that a signed token is readable by anyone, with no key at all:

```python
import base64
import hashlib
import hmac
import json

def b64(d): return base64.urlsafe_b64encode(json.dumps(d).encode()).rstrip(b"=").decode()
head, body = b64({"alg": "HS256", "typ": "JWT"}), b64({"sub": "maya", "role": "admin", "exp": 1760000000})
signature = base64.urlsafe_b64encode(hmac.new(b"server-key", f"{head}.{body}".encode(), hashlib.sha256).digest()).rstrip(b"=").decode()
token = f"{head}.{body}.{signature}"
payload = token.split(".")[1]
print("decoded payload with no key:", json.loads(base64.urlsafe_b64decode(payload + "=" * (-len(payload) % 4))))
# decoded payload with no key: {'sub': 'maya', 'role': 'admin', 'exp': 1760000000}
```

The signature stops anyone *changing* the claims without the key; it does nothing to hide them.

The practical distinction is where the application keeps state and how it validates requests. Server-managed sessions make centralized revocation straightforward. Self-contained tokens can allow services to validate requests without consulting a central session store on every request, but revocation and permission changes become harder to propagate before token expiry.

## OAuth and OpenID Connect: delegated access versus login identity

When an application lets you sign in through an identity provider, several distinct responsibilities may be involved. Two standards clarify those responsibilities: OAuth 2.0 and OpenID Connect (OIDC).

OAuth 2.0 is an authorization framework. It allows a client application to obtain limited access to a resource on behalf of a user or as itself, according to permissions granted by an authorization server. For example, a calendar application might receive permission to read calendar events without receiving the user's account password.

An access token represents the authority to access specified resources. The resource server validates that token and enforces its scope, audience, expiry, and other applicable constraints. OAuth is not, by itself, a protocol for proving a user's identity to the client.

OpenID Connect adds an identity layer on top of OAuth 2.0. It introduces an ID token, which communicates authentication-related claims about the user to the client. The client validates the token's issuer, audience, signature, expiry, and other required properties. The ID token and access token serve different purposes: the former tells the client about the authenticated user; the latter authorizes access to a resource.

A simplified sign-in flow looks like this:

1. The application redirects the user to an identity provider.
2. The identity provider authenticates the user, potentially using MFA.
3. The user grants any required consent, and the provider returns an authorization code.
4. The application exchanges the code through the appropriate flow to obtain tokens.
5. The application validates the identity information and establishes its own local session, or uses an appropriate token-based design.

In modern applications, the Authorization Code flow with PKCE is the standard choice for public clients and is also useful for confidential clients. PKCE binds the authorization-code exchange to the client instance that initiated it, reducing the risk that an intercepted code can be redeemed by an attacker.

OAuth/OIDC do not remove the need for application security. Redirect URIs must be validated, tokens must be handled carefully, and the application must distinguish the identity provider's claims from its own authorization decisions. Knowing who a user is does not automatically determine what that user should be allowed to do.

## The complete authentication lifecycle

These mechanisms fit together as layers rather than competing alternatives. A password or passkey, potentially combined with MFA, establishes evidence of identity. An identity provider may communicate that authentication through OIDC. The application then establishes a local session or uses tokens to maintain access. On each request, the system validates the relevant credential and separately determines whether the requested action is permitted.

This final distinction is fundamental: authentication asks who or what is making the request; authorization asks what that identity is allowed to do. A successfully authenticated user can still be denied access to an administrative endpoint. Conversely, a valid access token does not necessarily prove that the human presenting it is currently present; it proves only what the token's issuance and validation rules establish.

The lifecycle also has a time dimension. Credentials expire, sessions are revoked, tokens are refreshed, permissions change, and accounts may be disabled. Good authentication architecture considers not just how access begins, but how it is limited, monitored, and terminated. The most secure design is not necessarily the one with the most layers; it is the one whose mechanisms match the threat model and whose failure modes are understood.

<Callout type="pitfall">
Do not put secrets in a JWT payload, do not treat "the token is valid" as "the user is allowed", and do not accept tokens without checking issuer, audience and expiry. Also remember that a stolen session cookie or token bypasses the password and MFA entirely, so protect it with `Secure`, `HttpOnly` and `SameSite` cookies and short lifetimes.
</Callout>
