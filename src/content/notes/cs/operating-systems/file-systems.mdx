A file system is the layer that turns raw storage blocks into named files and directories while tracking where data lives, who can access it, and how changes persist. Three mechanisms explain much of how file systems work: inodes store file metadata and references to data, allocation methods determine how file contents occupy storage, and journaling helps the system recover from interrupted updates. The key distinction is between a file's identity, the location of its contents, and the consistency of the structures that connect them.

## A File Name Is Not the File's Identity

When a program opens `/home/alex/report.txt`, the file system must translate a human-readable path into the object representing the file and then locate its contents.

A directory is essentially a mapping from names to file-system objects. In a Unix-like file system, a directory entry associates a filename with an **inode** number. The inode stores metadata such as file permissions, ownership, size, timestamps, and references to the blocks containing the file's data.

The filename is therefore not necessarily stored inside the inode itself. It is stored in the directory entry that points to the inode.

```
directory entry          inode 42                               data blocks
"report.txt" → 42  ──►  owner, mode, size, timestamps,   ──►  812, 813, 2190
                         block pointers  (no filename!)        (the actual bytes)
```

This separation explains several behaviors in Unix-like systems.

- **Hard links:** Multiple directory entries can refer to the same inode, giving one file object multiple names.
- **Renaming:** Renaming a file within a file system can often change directory entries without moving the file's data blocks.
- **Unlinking:** Removing a filename does not necessarily delete the underlying data immediately. If another hard link exists, or a process still has the file open, the inode and data can remain in use.

You can watch this happen from Python, which exposes the inode number and the link count through `os.stat`:

```python
import os, tempfile

d = tempfile.mkdtemp()
a = os.path.join(d, "report.txt")
b = os.path.join(d, "alias.txt")
with open(a, "w") as f:
    f.write("hello")

os.link(a, b)                     # a second directory entry for the same file
print(os.stat(a).st_ino == os.stat(b).st_ino, os.stat(a).st_nlink)   # True 2
os.remove(a)                      # removes one name, not the file
print(open(b).read(), os.stat(b).st_nlink)                           # hello 1
```

An inode is not a universal feature of every file system. NTFS, FAT, and other formats organize metadata differently, even though they solve similar problems.

## Allocation Methods: Where the Data Goes

The file system must map a file's logical byte positions to physical storage locations. The allocation method determines how that mapping is represented and what trade-offs it creates.

### Contiguous allocation

A file occupies a sequence of consecutive disk blocks. The file system can locate a block using the file's starting block and its length.

If a file starts at block $b$, its logical block $i$ is located at

$$
\text{block}(i) = b + i

$$

This makes sequential access simple and efficient, and direct access is also straightforward. The difficulty is growth: extending a file may require finding enough adjacent free blocks or moving the file. Over time, free space can become fragmented into small gaps.

### Linked allocation

Each block points to the next block in the file. Blocks can be scattered throughout the storage device, so files can grow without requiring adjacent free space.

The trade-off is access cost. Sequential reading is natural, but reaching a particular logical block may require following a chain of earlier blocks. A corrupted pointer can also disrupt access to the remaining chain. File Allocation Table (FAT) systems use a table to represent these links rather than storing every next-block pointer directly inside each data block.

### Indexed allocation

An index structure records the locations of a file's data blocks. The file system can use that index to find a particular logical block without traversing all preceding data blocks.

Unix-style inode systems commonly use block pointers, sometimes with indirect blocks, while modern designs may use extent trees or other structures. An extent represents a contiguous run of blocks, allowing one metadata entry to describe many blocks when the file is stored in large sequential regions.

| Method     | Main advantage                                | Main limitation                               |
| ---------- | --------------------------------------------- | --------------------------------------------- |
| Contiguous | Fast sequential and direct access             | Growth and external fragmentation             |
| Linked     | Easy to grow; blocks need not be adjacent     | Slow random access and pointer overhead       |
| Indexed    | Efficient block lookup and flexible placement | Index metadata consumes space                 |
| Extents    | Compact mapping for contiguous runs           | Fragmentation can increase mapping complexity |

Modern file systems often combine ideas rather than using one pure allocation method. For example, an inode may reference a tree of extents, each describing a run of contiguous blocks.

## Journaling: Recovering from Interrupted Updates

Writing a file often requires more than writing its data bytes. The file system may also need to update allocation metadata, inode information, directory entries, and free-space structures.

Imagine creating a new file. The file system might allocate a data block, update the inode, and insert a directory entry. If power fails after only some of these changes reach storage, the file system could be left with inconsistent metadata: a directory entry pointing to incomplete state, or a block marked as allocated without a valid owner.

A **journal** records information about intended file-system changes so that interrupted updates can be recovered consistently. A common approach is to record the relevant transaction in the journal, ensure the required journal information is durable, and then apply the changes to their normal locations. After a crash, recovery examines the journal to determine which operations can safely be replayed or discarded.

### Simplified journaled update

1. Record the metadata transaction in the journal.
2. Make the journal record durable according to the file system's ordering rules.
3. Apply the transaction to the main file-system structures.
4. Mark the transaction complete or reclaim its journal space.

This is a conceptual sequence, not a universal implementation. Some file systems journal metadata only; others support different data-journaling modes. Ordering and durability guarantees vary.

<Callout type="pitfall" title="Journaling protects structure, not your data">
Journaling does not automatically guarantee that every recent file-data write survives a crash. Applications that need durability must call `fsync()` (or open files with the right flags); databases do exactly this before reporting a commit.
</Callout>

A critical distinction is that journaling does not automatically guarantee that every recent file-data write survives a crash. A metadata-journaling file system may recover its structural consistency while still losing recently written data or leaving the newest file contents incomplete. Application-level durability also depends on write ordering, caching, and whether the application and operating system explicitly request that data be synchronized to storage.

Journaling primarily reduces the need to reconstruct file-system consistency from scratch after a crash. It does not replace backups, eliminate hardware failure, or prevent every form of data corruption.

## Putting the Three Mechanisms Together

Consider saving an edited document.

The directory maps its name to an inode or equivalent metadata object. The inode's allocation structures identify the blocks or extents containing the document's bytes. When the document grows, the file system updates its allocation metadata and size. If journaling is used, the file system records the appropriate changes so it can recover from an interruption without leaving the metadata structures in an inconsistent state.

These mechanisms address separate questions:

- **Inode or metadata structure:** What is this file, and what attributes and storage references describe it?
- **Allocation method:** Where are the file's contents stored, and how do logical offsets map to storage blocks?
- **Journaling:** How can related updates be recovered if a crash interrupts them?

The broader lesson is that a file system is not merely a table of filenames and disk addresses. It is a coordinated data structure whose naming, allocation, permissions, and persistence rules must remain consistent as files are created, modified, moved, and deleted.
