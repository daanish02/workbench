Big-O answers one question: when the input grows, how much more work does the program do? You compare growth rates, not seconds, so an `O(n²)` program that is fast on 100 items can still fail on a million. The [Big-O note](../../algorithms/big-o-notation/) explains where the notation comes from. This page is the lookup table.

## Growth Rates

Counting basic steps makes the growth visible. The script below counts steps rather than timing them, so the output is the same on every machine. It compares a linear scan, a binary search and a nested loop over the same inputs.

```python
# Count basic steps, not seconds, so the output is the same on every machine.
def linear_steps(items, target):
    steps = 0
    for x in items:
        steps += 1
        if x == target:
            break
    return steps

def binary_steps(items, target):
    lo, hi, steps = 0, len(items) - 1, 0
    while lo <= hi:
        steps += 1
        mid = (lo + hi) // 2
        if items[mid] == target:
            break
        if items[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    return steps

def pair_steps(n):
    steps = 0
    for i in range(n):
        for j in range(n):
            steps += 1
    return steps

print(f"{'n':>8} {'linear':>8} {'binary':>8} {'pairs':>12}")
for n in [10, 100, 1_000, 10_000]:
    items = list(range(n))
    pairs = pair_steps(n) if n <= 100 else n * n  # check the formula where it is cheap to run
    print(f"{n:>8} {linear_steps(items, n - 1):>8} {binary_steps(items, n - 1):>8} {pairs:>12}")
```

```text
       n   linear   binary        pairs
      10       10        4          100
     100      100        7        10000
    1000     1000       10      1000000
   10000    10000       14    100000000
```

In words: the linear scan's count equals `n`, so it grows in step with the input. Binary search halves the remaining range each step, so going from 10,000 to 10 times more items adds only about 10 more steps. The nested loop does `n` steps for each of `n` outer iterations, so 10 times more input costs 100 times more work.

### Sorting

| Algorithm | Best | Average | Worst | Extra space | Stable |
| --- | --- | --- | --- | --- | --- |
| Insertion sort | `O(n)` | `O(n²)` | `O(n²)` | `O(1)` | Yes |
| Merge sort | `O(n log n)` | `O(n log n)` | `O(n log n)` | `O(n)` | Yes |
| Quicksort | `O(n log n)` | `O(n log n)` | `O(n²)` | `O(log n)` | No |
| Heapsort | `O(n log n)` | `O(n log n)` | `O(n log n)` | `O(1)` | No |
| Counting sort | `O(n + k)` | `O(n + k)` | `O(n + k)` | `O(n + k)` | Yes |

`k` is the range of the keys. Counting sort only applies to small integer-like keys.

## Reading a Bound

Drop constants and lower-order terms: `5n² + 3n + 100` is `O(n²)`. Multiply the work of nested loops and add the work of sequential steps: a loop inside a loop is `O(n · m)`, and two loops in a row are `O(n + m)`. Recursion is often `O(branches^depth)` or, for divide-and-conquer, a recurrence like `T(n) = 2T(n/2) + O(n)`, which gives `O(n log n)`.

Big-O hides the constant. Two `O(n log n)` sorts can differ several-fold in practice because of cache behaviour, so benchmark the realistic input size before choosing.
