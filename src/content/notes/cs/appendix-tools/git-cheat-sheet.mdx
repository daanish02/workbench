Git stores history as a graph of commits, and every command moves something in that picture: a file in your **working tree**, a file in the **staging area** (the index), or a pointer such as a branch. The [Git](../../software-engineering/git-internals/) note explains that model and why it works the way it does; [Code Review](../../software-engineering/code-review/) and [CI/CD](../../software-engineering/ci-cd/) cover the practices around pull requests. This page is the working reference: two searchable tables (Git, then the GitHub CLI `gh`), followed by the everyday workflows written out step by step, history editing, and recovery.

## Everyday Workflow

The branch-and-pull-request cycle, from an up-to-date `main` to a merged change, with Git doing the local work and `gh` the GitHub side:

```bash
git switch main && git pull                      # start from the latest main
git switch -c fix/empty-input                    # one branch per change
# … edit files …
git add -p                                       # review and stage hunk by hunk
git commit -m "fix: handle empty input in parser"
git push -u origin fix/empty-input               # publish the branch, set upstream
gh pr create --fill --reviewer ana               # title and body from the commits
gh pr checks --watch                             # wait for CI
# … reviewer asks for a change …
git commit -am "test: cover the empty case"
git push                                         # the pull request updates itself
gh pr merge --squash --delete-branch             # merge as one commit, delete the branch
git switch main && git pull && git branch -d fix/empty-input
```

Keep each branch to one logical change, small enough to review in one sitting ([Code Review](../../software-engineering/code-review/)). Squash-merging gives `main` one commit per pull request; merge commits keep every branch commit; rebase-merging replays them linearly. Teams pick one and set it in the repository settings.

**Keeping a branch up to date with `main`.** On your own branch, rebase so history stays linear, then force-push safely:

```bash
git fetch origin
git rebase origin/main               # replay your commits on the latest main
# conflict? edit the files, then:
git add <resolved-files> && git rebase --continue
git push --force-with-lease          # refuses if someone else pushed in the meantime
```

On a branch others also push to, merge instead (`git merge origin/main`), because rebasing rewrites commits they already have.

**Resolving a conflict.** Git marks the conflicting region in each file:

```text
<<<<<<< HEAD (yours, or the branch being rebased onto)
timeout = 30
=======
timeout = 60
>>>>>>> fix/slow-network (theirs, or the commit being replayed)
```

Edit the file to the correct final content, remove the markers, `git add` it, and continue the merge or rebase. `git diff` during a conflict shows only the unresolved parts; `git checkout --ours` or `--theirs` takes one side wholesale.

**Working on a fork.** `gh repo fork org/project --clone` creates the fork, clones it and adds `upstream`. Sync with `gh repo sync` (on GitHub) or `git fetch upstream && git rebase upstream/main` (locally), push branches to your fork, and `gh pr create` opens the pull request against the original.

## Editing History

Before a branch is shared, rewriting its commits makes the history easier to review. **Interactive rebase** opens a list of commits as a todo file:

```text
pick a1b2c3d add search endpoint
fixup 9f8e7d6 fix typo in search
reword 4c5d6e7 add tests              # change this commit's message
drop 0a1b2c3 debug logging            # remove this commit entirely
```

Reorder lines to reorder commits; `squash` merges a commit into the previous one and combines the messages, `fixup` does the same but drops its message, and `edit` stops so you can amend. The `--fixup` plus `--autosquash` pair automates the common case: commit a fix with `git commit --fixup <commit>` and the next `git rebase -i --autosquash main` places and squashes it for you. If a rebase goes wrong, `git rebase --abort` returns to the starting point, and after it finishes, the reflog still holds the old commits.

## Finding the Bad Commit

`git bisect` binary-searches history: mark one commit bad and one good, test the middle, repeat. With 1000 commits between them it needs about 10 steps, and it can run a test script by itself:

```bash
git bisect start
git bisect bad                    # the current commit is broken
git bisect good v1.4.0            # this release worked
git bisect run uv run pytest tests/test_parser.py   # exit code 0 = good, non-zero = bad
git bisect reset                  # back to where you started
```

## Recovering Lost Work

The **reflog** records every position `HEAD` has had, including commits no branch points to any more, for about 90 days. This script creates a throwaway repository, loses two commits with `reset --hard`, and gets them back:

```python
import os
import subprocess
import tempfile

ENV = {**os.environ, "GIT_AUTHOR_NAME": "Ada", "GIT_AUTHOR_EMAIL": "ada@example.com",
       "GIT_COMMITTER_NAME": "Ada", "GIT_COMMITTER_EMAIL": "ada@example.com",
       "GIT_AUTHOR_DATE": "2026-01-01T12:00:00Z", "GIT_COMMITTER_DATE": "2026-01-01T12:00:00Z",
       "GIT_CONFIG_GLOBAL": os.devnull, "GIT_CONFIG_NOSYSTEM": "1"}   # ignore personal config: same hashes everywhere

def git(*args):
    return subprocess.run(["git", *args], cwd=repo, env=ENV, capture_output=True, text=True, check=True).stdout.strip()

with tempfile.TemporaryDirectory() as repo:
    git("init", "-q", "-b", "main")
    for msg in ["add parser", "add tests", "fix edge case"]:
        with open(os.path.join(repo, "log.txt"), "a", newline="\n") as f:   # LF on every OS
            f.write(msg + "\n")
        git("add", "log.txt")
        git("commit", "-q", "-m", msg)
    print(git("log", "--oneline"))
    git("reset", "-q", "--hard", "HEAD~2")              # oops: two commits gone from the branch
    print("after reset:", git("log", "--oneline"))
    print(git("reflog", "-4", "--format=%h %gs"))       # but HEAD's history remembers them
    git("reset", "-q", "--hard", "HEAD@{1}")            # back to where HEAD was before the reset
    print("recovered:", git("log", "--oneline", "-1"))
# 89b3217 fix edge case
# 13d9d0e add tests
# cc0c8e6 add parser
# after reset: cc0c8e6 add parser
# cc0c8e6 reset: moving to HEAD~2
# 89b3217 commit: fix edge case
# 13d9d0e commit: add tests
# cc0c8e6 commit (initial): add parser
# recovered: 89b3217 fix edge case
```

In words: after the reset the branch shows only "add parser", but the reflog's newest entry records the reset and the entries below it still name the lost commits. `HEAD@{1}` means "where `HEAD` was one move ago", so resetting to it restores "fix edge case" with the same hash, 89b3217, because a commit is identified by its content, parents, author, dates and message, all fixed here. What the reflog cannot recover is work that was never committed: changes discarded by `git restore` or `git reset --hard` before any commit are gone.

Other common rescues:

- **Committed to the wrong branch**: `git branch fix-branch` (keep the commit), `git reset --hard HEAD~1` (remove it here), `git switch fix-branch`.
- **Pushed a bad commit to a shared branch**: do not rewrite it; `git revert <commit>` adds a commit that undoes it.
- **Committed a secret**: rotate the secret first (it is compromised once pushed), then remove it from history with `git filter-repo` and force-push; deleting it in a new commit leaves it in history.
- **Messed-up rebase**: `git reflog`, find the entry before `rebase (start)`, `git reset --hard <that entry>`.

<Callout type="pitfall">
`git reset --hard`, `git restore`, `git clean -fd` and `git checkout -- <file>` discard uncommitted changes with no undo, because the reflog only knows about commits. Run `git status` and `git diff` first, and `git stash -u` instead if you are not sure. On shared branches, never rewrite pushed history (`rebase`, `--amend`, `reset` followed by a force-push) without agreement: teammates' copies diverge, and `--force` (unlike `--force-with-lease`) silently deletes commits others pushed.
</Callout>

## Hygiene

- **Commit messages**: a short imperative subject ("fix: handle empty input"), a blank line, then why the change was made. Conventions such as Conventional Commits let tools generate changelogs.
- **`.gitignore`** (see [Ignore Files](../ignore-files-sheet/)): keep build output, dependencies, local environments and secrets (`.env`) out of the repository from the start; `git rm --cached` stops tracking a file that was committed by mistake.
- **Signed commits**: `git config --global commit.gpgsign true` with a GPG or SSH key shows "Verified" on GitHub.
- **Protected branches**: require pull requests, reviews and passing checks before anything reaches `main` (repository settings or `gh api` with the branch-protection endpoints).
- **Hooks**: scripts in `.git/hooks` (or managed with pre-commit or lefthook) run linters and tests before commits and pushes.

Most commands follow one shape: `git <command> [options] [arguments]`, and `gh <noun> <verb> [flags]`. When a command is unfamiliar, `git <command> --help` and `gh <command> --help` give every option.
