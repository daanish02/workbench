Many programs ask the same kind of question over and over: total sales between two dates, the minimum temperature in a window, how many events fell in a time range. With the data in an [array](../arrays-and-strings/), each question is a loop over a slice, $O(n)$ per query; with $q$ queries on a million elements, that is $q$ million steps. **Range-query structures** spend some memory and setup time so that each query, and each change to the data, costs $O(1)$ or $O(\log n)$ instead. This note covers **prefix sums** for data that does not change, the **segment tree** for any associative operation with updates, and the compact **Fenwick tree** for sums with updates. It builds on the binary [trees](../trees/) and the bit tricks in [Number Representation](../../foundations/number-representation/).

## Prefix Sums

A **prefix sum** array stores, at position $i$, the sum of the first $i$ elements:

$$
P[0] = 0, \qquad P[i] = a[0] + a[1] + \dots + a[i-1].

$$

In words: every range sum is then the difference of two prefixes, $\text{sum}(a[l..r]) = P[r+1] - P[l]$, because the first $l$ elements cancel.

```python
from itertools import accumulate

a = [5, 2, 8, 1, 9, 3, 7, 4]
prefix = [0] + list(accumulate(a))             # prefix[i] = sum of a[0:i]

def range_sum(l, r):                           # sum of a[l..r], inclusive, in two lookups
    return prefix[r + 1] - prefix[l]

print("prefix:", prefix)
print("sum a[2..5]:", range_sum(2, 5), "| check:", sum(a[2:6]))
a[3] += 10                                     # one update invalidates every later prefix entry
print("stale answer:", range_sum(2, 5), "| true:", sum(a[2:6]))
# prefix: [0, 5, 7, 15, 16, 25, 28, 35, 39]
# sum a[2..5]: 21 | check: 21
# stale answer: 21 | true: 31
```

In words: the sum of `a[2..5]` is `prefix[6] - prefix[2] = 28 - 7 = 21`, two lookups regardless of the range length. The weakness shows in the last line: after `a[3] += 10` the prefix array still says 21 while the true sum is 31, and fixing it means recomputing every entry from index 4 on, $O(n)$ per update. Prefix sums suit data that is built once and queried many times. The same idea works in two dimensions (summed-area tables for image regions), and for any operation with an inverse (XOR, counts), but not for min or max, which cannot be "subtracted".

<Callout type="pitfall">
Off-by-one errors are the usual bug: decide once whether ranges are inclusive (`a[l..r]`) or half-open (`a[l:r]`), and keep the leading `0` in the prefix array so that ranges starting at index 0 need no special case.
</Callout>

## Segment Trees

A **segment tree** is a binary tree over the array. Each leaf holds one element; each internal node holds the aggregate (here, the sum) of the leaves below it, so the root covers the whole array, its children cover each half, and so on. A query for `a[l..r]` combines the few nodes whose ranges fit exactly inside it, at most two per level, so $O(\log n)$ nodes. A point update changes one leaf and recomputes its $O(\log n)$ ancestors.

The tree fits in an array of size $2n$: leaves at positions $n$ to $2n - 1$, and node $i$ has children $2i$ and $2i + 1$. The iterative version below climbs from both ends of the range at once:

```python
class SegmentTree:
    def __init__(self, a):
        self.n = len(a)
        self.t = [0] * self.n + list(a)        # leaves at t[n..2n-1], node i has children 2i and 2i+1
        for i in range(self.n - 1, 0, -1):
            self.t[i] = self.t[2 * i] + self.t[2 * i + 1]

    def update(self, i, value):
        i += self.n
        self.t[i] = value
        while i > 1:                           # recompute each ancestor: O(log n) nodes
            i //= 2
            self.t[i] = self.t[2 * i] + self.t[2 * i + 1]

    def query(self, l, r):                     # sum of a[l..r] inclusive
        total, l, r = 0, l + self.n, r + self.n + 1
        touched = 0
        while l < r:                           # climb from both ends, taking nodes that lie fully inside
            if l & 1:
                total += self.t[l]; l += 1; touched += 1
            if r & 1:
                r -= 1; total += self.t[r]; touched += 1
            l //= 2; r //= 2
        return total, touched

a = [5, 2, 8, 1, 9, 3, 7, 4]
st = SegmentTree(a)
total, touched = st.query(1, 6)
print("sum a[1..6]:", total, "from", touched, "nodes | check:", sum(a[1:7]))
st.update(3, 11)
a[3] = 11
print("after update:", st.query(1, 6)[0], "| check:", sum(a[1:7]))

import random
rng = random.Random(0)
big = [rng.randint(0, 100) for _ in range(1 << 16)]
st = SegmentTree(big)
total, touched = st.query(123, 60_000)
print("n = 65536: correct:", total == sum(big[123:60_001]), "| nodes added:", touched, "vs elements:", 60_000 - 123 + 1)
# sum a[1..6]: 30 from 4 nodes | check: 30
# after update: 40 | check: 40
# n = 65536: correct: True | nodes added: 17 vs elements: 59878
```

In words: the sum of `a[1..6]` (six elements) comes from 4 tree nodes: the leaves for `a[1]` and `a[6]` and the two nodes covering `a[2..3]` and `a[4..5]`. Setting `a[3] = 11` updates one leaf and its 3 ancestors, and the next query gives 40, matching a direct sum. On 65,536 elements, a range of 59,878 elements is answered by adding just 17 nodes, about $2 \log_2 n$.

Replace `+` with `min`, `max`, `gcd` or any other **associative** operation (one where grouping does not matter) and the same code answers those queries; the identity value (0 for sums, $+\infty$ for min) starts the total. With **lazy propagation**, where a node stores a pending update for its whole range and pushes it down only when needed, a segment tree also supports range updates ("add 5 to `a[l..r]`") in $O(\log n)$.

## Fenwick Trees

A **Fenwick tree** (or **binary indexed tree**) supports prefix sums and point updates in $O(\log n)$ with less code and memory than a segment tree. It uses 1-based indices, and `tree[i]` stores the sum of the $\text{lowbit}(i)$ elements ending at position $i$, where $\text{lowbit}(i)$ is the value of $i$'s lowest set bit, computed as `i & -i` in two's complement. For example, `tree[12]` (`1100` in binary, lowbit 4) holds the sum of elements 9 to 12.

- A **prefix sum** up to $i$ adds `tree[i]`, then removes the lowest set bit of $i$ and repeats until $i = 0$.
- An **update** at $i$ adds the change to `tree[i]`, then *adds* the lowest set bit to $i$ and repeats while $i \le n$, reaching every node whose range covers $i$.

Each step clears or carries one bit, so both loops take at most $\log_2 n + 1$ steps.

```python
class Fenwick:
    def __init__(self, n):
        self.tree = [0] * (n + 1)              # 1-indexed; tree[i] covers the lowbit(i) elements ending at i

    def add(self, i, delta):                   # a[i] += delta, i is 0-based
        i += 1
        while i < len(self.tree):
            self.tree[i] += delta
            i += i & -i                        # jump to the next node whose range covers i

    def prefix(self, i):                       # sum of a[0..i-1]
        total = 0
        while i > 0:
            total += self.tree[i]
            i -= i & -i                        # drop the lowest set bit
        return total

    def range_sum(self, l, r):
        return self.prefix(r + 1) - self.prefix(l)

a = [5, 2, 8, 1, 9, 3, 7, 4]
fw = Fenwick(len(a))
for i, x in enumerate(a):
    fw.add(i, x)
print("tree:", fw.tree)
print("sum a[2..5]:", fw.range_sum(2, 5), "| check:", sum(a[2:6]))
fw.add(3, 10)
a[3] += 10
print("after a[3] += 10:", fw.range_sum(2, 5), "| check:", sum(a[2:6]))

i, path = 13, []
while i > 0:                                   # the nodes prefix(13) reads in a 16-element tree
    path.append(i)
    i -= i & -i
print("prefix(13) reads tree", path, "=", [format(p, "04b") for p in path])

import random
rng = random.Random(1)
n = 1000
b, fw = [0] * n, Fenwick(n)
for _ in range(5000):                          # random updates and queries against a plain list
    i, d = rng.randrange(n), rng.randint(-50, 50)
    b[i] += d
    fw.add(i, d)
l, r = sorted(rng.sample(range(n), 2))
print("matches brute force:", fw.range_sum(l, r) == sum(b[l:r + 1]))
# tree: [0, 5, 7, 8, 16, 9, 12, 7, 39]
# sum a[2..5]: 21 | check: 21
# after a[3] += 10: 31 | check: 31
# prefix(13) reads tree [13, 12, 8] = ['1101', '1100', '1000']
# matches brute force: True
```

In words: `tree[4] = 16` is the sum of the first four elements (5 + 2 + 8 + 1), `tree[6] = 12` covers elements 5 and 6 (9 + 3), and `tree[8] = 39` is the whole array. Unlike prefix sums, the update `a[3] += 10` is $O(\log n)$, and the range sum correctly becomes 31. The prefix of 13 reads only three nodes, one per set bit of `1101`: `tree[13]`, `tree[12]` and `tree[8]`. After 5,000 random updates on 1,000 elements, a random range sum still matches the brute-force sum.

<Callout type="pitfall">
A Fenwick tree answers range queries only for operations with an inverse, because a range is computed as `prefix(r + 1) - prefix(l)`. For range minimum or maximum, use a segment tree (or a sparse table if the data never changes).
</Callout>

## Choosing a Structure

| Structure | Build | Query | Point update | Memory | Operations |
| --- | --- | --- | --- | --- | --- |
| Plain array | $O(1)$ | $O(n)$ | $O(1)$ | $n$ | Any |
| Prefix sums | $O(n)$ | $O(1)$ | $O(n)$ | $n + 1$ | Invertible (sum, XOR, count) |
| Fenwick tree | $O(n \log n)$, or $O(n)$ with care | $O(\log n)$ | $O(\log n)$ | $n + 1$ | Invertible |
| Segment tree | $O(n)$ | $O(\log n)$ | $O(\log n)$ | $2n$ | Any associative; range updates with lazy propagation |
| Sparse table | $O(n \log n)$ | $O(1)$ for min/max | Rebuild | $n \log n$ | Idempotent (min, max, gcd) |

<Callout type="key">
All of these trade setup and memory for query speed by **precomputing aggregates of blocks**: prefix sums use blocks that start at 0, Fenwick trees use power-of-two blocks named by the lowest set bit, and segment trees use a full binary hierarchy. Pick the simplest one whose update and operation needs match the workload.
</Callout>
